# Responda database design

## Core reporting rule

A citizen report and a confirmed emergency incident are different records:

- `reports` stores each submission from a citizen or authorized staff member.
- `incidents` stores the emergency confirmed by staff.
- Multiple reports can reference the same incident, preventing duplicate dispatches.
- `response_assignments` references an incident, not an individual report.

## Online and offline mobile reports

- Online app submissions use `reports.source = app_api`.
- Offline app submissions sent through SMS use `reports.source = app_sms`.
- Both carry the same unique `client_report_id`, which prevents the SMS and a later API retry
  from creating two reports.

## Strict app-only SMS gateway policy

The gateway accepts emergency reports only when the SMS was generated by the Responda app.
An accepted SMS must have all of the following:

1. A supported Responda SMS protocol version.
2. A `client_report_id` generated by the app.
3. A digital signature that the backend verifies successfully.
4. A structured payload that passes validation.
5. A gateway message identifier that has not already been processed.

The `sms_messages` constraints prevent an unsigned message from being marked `accepted` or linked
to a report. Any ordinary, malformed, duplicate, or invalidly signed SMS is marked `rejected`,
`duplicate`, or `error`. It does not create a report and does not appear as an emergency on the
dashboard. Its raw contents may be retained in the gateway log for troubleshooting and auditing.

Filtering by the sender's phone number alone is not sufficient because phone numbers can be
spoofed. The digital signature is the source-of-origin check.

## Machine learning boundaries

- `report_translations` stores the translated English description while `reports` preserves the
  citizen's original words.
- `priority_assessments` stores the ML priority recommendation, model version, and confidence.
- `reports.final_priority` is the staff-confirmed priority.
- ML does not choose the incident type; the reporter selects it and staff may verify it.

## Location storage

The current PostgreSQL installation does not provide PostGIS, so locations use validated decimal
latitude and longitude columns. A later migration can add PostGIS geography columns when the
extension is installed.
